# 回答言語

- 入力された言語にかかわらず、常に日本語で回答してください。

# 自律的な修正の実行

- 自律的に修正してよいのは、ユーザーが明示的に指示した時のみとする。
- それ以外の通常のやり取りでは、修正内容を提示して確認を得てから実行する。

# サブエージェントとタスクの委任

- 独立した調査・レビューや並列化が有効な作業は委任し、単純な修正や分割の効果がない作業では起動しない。
- 役割・モデル・reasoning effort は各 agent の TOML 定義に従う。`scout` は事実の探索に限定し、原因分析や評価は任せない。実装と関連検証は同じ担当にまとめる。
- reviewer は変更せず、通常は 1 担当とする。追加の専門観点が必要な場合だけ、異なる範囲を割り当てて増やす。
- 依頼には目的・要件・制約・担当範囲・完了条件・変更可能なファイルを明示し、必要な背景に応じて履歴を継承する。独立レビューには差分と関連コードを渡し、主担当の結論の共有は最小限にする。
- 独立した作業・ツール操作はまとめて並列実行し、依存する作業は前提の結果を確認してから進める。
- 同一ファイルの編集担当は 1 人に限定する。主担当は重複・競合を防ぎ、差分と検証結果を確認して成果物とレビュー指摘を統合し、最終検証を行う。
- 続きの仕事は可能なら既存の担当へ依頼し、不足する背景は主担当が補足する。

# ドキュメントと技術文書の適正化

* ドキュメントと既存のコードが食い違うときはコードの書き方に従い、見つけた食い違いを最後の返答ですべて挙げること。
* README、`docs/`、設計書、ADR、API 仕様、運用手順などを作成・更新する際は、網羅性や文章量を目的化せず、想定読者が理解・判断・実行するために必要な情報だけを記述してください。
* 背景の過剰な説明、既知情報の言い換え、同一内容の重複、実装から推測した未確定事項、利用される見込みのない例や補足は追加しないでください。
* 文書の新規作成・大幅な更新では、原則として実装や初稿を担当していない `docs-reviewer` にレビューを依頼してください。軽微な修正では省略して構いません。
* 依頼には文書の目的・想定読者・要件・受け入れ条件・制約・対象文書・関連する実装や仕様、差分を含めてください。履歴継承と独立性は共通の委任ルールに従ってください。
* 指摘は実装・仕様・ユーザーの要望と照合し、必要性と正確性を確認して反映してください。

# 開発スタイル

- TDD で開発する（探索 → Red → Green → Refactoring）
- KPI やカバレッジ目標が与えられたら、達成するまで試行する。
- ユーザーの要望や要件が不明確な場合は、質問を繰り返し詳細を掘り下げ、曖昧な点を明確にしてください。

# コミット前の確認

- lint, format, type check は全体実行して構いません。
- テスト・build は変更の影響範囲に限定し、全体実行はコミット・push・PR 作成時も remote の ci/cd に任せてください。明示的に依頼された場合のみローカルで全体実行してください。
- テスト・build の対象を絞れない場合は、その旨を報告し、全体実行へ切り替えないでください。

# 設計原則

- UIでは、不要なセカンダリラベルや説明を避ける。レイアウトに説明させる。
- 最小限の変更で実装することに固執せず、設計の簡潔さと正確さを優先してください。
- コントラクト層（API/型）を厳密に定義し、実装層は再生成可能に保つようにしてください。
- 関心の分離を保ってください。
- 状態とロジックを分離してください。
- ユーザーから明示的な要望がない限り、後方互換性のための補助機能や代替経路の実装は行わないでください。
